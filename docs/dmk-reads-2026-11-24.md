# DMK reads, 2026-11-24

The disk controller reads double-density 5.25-inch DMK images, read only
(`components/coco/fdc/fdc.c`). An image is refused at insert unless its
header, size and every track's table of ID pointers are consistent.

## What the controller does with a DMK

- **Read Sector** takes the first ID whose track and sector match the
  track and sector registers (the ID's track number, not the head's) and
  whose ID CRC is right. Its data mark (`A1 A1 A1 FB` or `F8`) must follow
  within 43 bytes of the ID's last CRC byte, as the WD1793 data sheet gives
  for double density. Otherwise the search goes on and ends in Record Not
  Found. The field is then read whatever bytes follow, so a sector's data
  may run over the next sector's ID. `F8` sets the record-type bit, a bad
  data CRC the CRC bit, and Read Sector Multiple stops there. The sector
  size is the ID's size code's low two bits, as MAME has it.
- **Read Address** returns the track's IDs in turn and puts the ID's track
  in the sector register. A bad ID CRC sets the CRC bit.
- **Read Track** returns the track's raw bytes after the pointer table.
- **Write Sector** and **Write Track** end with Write Protect. A
  write-protected JVC image now refuses Write Track too.

The drive does not turn: a sector is found after the same short search
wherever its ID is on the track.

## Checks

- `make -C components/coco/host check-dmk` builds `dmk_fixture.py`'s track
  (seven IDs out of order on the track's ID 7: a deleted-data sector, a
  256-byte one, a bad data CRC, a sector whose data runs over the next
  ID, an ID with no data mark, a data mark 60 bytes late and size code 4)
  and an image with a bad pointer. `dmk_test` drives the controller's
  registers directly. It also passes with AddressSanitizer and UBSan.
- `components/coco/host/jvc2dmk.py` makes a DMK from a JVC image, the
  sectors interleaved 4 apart with standard gaps and CRCs computed by
  Python's `binascii`. Tiler Tex (`msnyder3.dsk`, CoCo 2, composite) and
  B.E. Break-In (`msnyder5.dsk`, CoCo 3) from the
  [software replays](software-replay-2026-11-24.md) were each run from the
  JVC and from its DMK. All nine captures and both PCM recordings are
  identical byte for byte.
- JVC controls: `DSKINI0`, `SAVE`, eject and insert, `LOAD`, `RUN` and
  `DIR` on a blank image. The image and the screen text are identical
  with the committed controller (`380a46a`) and the new one. That disk,
  converted to a DMK, gives `FREE(0)` 67, loads and runs its program, and
  answers `SAVE` and `DSKINI` with `?WP ERROR`, leaving the file unchanged.
- MaTouch (ESP-IDF 5.5.6, UART console): the web page lists `.dmk`. The
  fixture, uploaded and inserted, gave the host's results for Read
  Address, Read Sector (deleted data, bad CRC, the overlapping sector, the
  two Record Not Found cases, size code 4), Read Track's 6272 bytes and
  Write Protect on Write Sector and Write Track, through 6809 probe code
  loaded with the debugger. The Tiler Tex DMK listed its 12 programs with
  `DIR` and ran to the splash (59 fps, PMODE 3). It matched the morning's
  JVC splash on the board except for its two animated figures, captured on
  another frame. Both images downloaded back unchanged.

The Tab5 firmware builds; it was not flashed.

## Not done

Writes to DMK images, single-density or mixed-density tracks, track
lengths over `0x1900`, and rotation timing (Read Address in the order the
IDs pass the head, the index pulse against the raw track). DMK images of
protected CoCo titles from elsewhere have not been run: every DMK here was
made by `jvc2dmk.py` or the fixture.
